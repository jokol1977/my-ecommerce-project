# سیاست پایهٔ هویت و ورود

**وضعیت:** جریان ورود و MFA پیاده‌سازی و به‌صورت محلی آزموده شده؛ در محیط فعلی و به‌صورت پیش‌فرض ورود غیرفعال است چون سرویس/رازهای واقعی فراهم نشده‌اند.

## انتخاب‌های پیش‌فرض

- **مشتری:** ورود و ساخت حساب با کد شش‌رقمی یک‌بارمصرف به ایمیل. حساب تازه فقط با نقش `CUSTOMER` ساخته می‌شود؛ نقش، شناسه یا وضعیت حساب از ورودی کاربر پذیرفته نمی‌شود.
- **کد ایمیل:** مهلت ۱۰ دقیقه، حداکثر ۵ تلاش برای هر کد، مصرف اتمیک و یک‌باره، نگهداری فقط به‌صورت hash و پاسخ یکسان برای ایمیل موجود و ناموجود تا وجود حساب افشا نشود.
- **محدودسازی:** حداکثر ۵ درخواست ارسال برای هر ایمیل و ۵ درخواست از هر IP در ۱۵ دقیقه؛ تلاش‌های بررسی کد نیز با Redis مشترک در تولید محدود می‌شوند. تولید بدون Redis سالم و IP معتبر از Nginx نباید ورود را فعال کند.
- **مدیر:** همان تأیید ایمیل به‌علاوهٔ TOTP اجباری. جلسهٔ مدیر بدون ثبت موفق عامل دوم ساخته یا پذیرفته نشود. کلید TOTP با AES-256-GCM و کلید جداگانهٔ `AUTH_MFA_ENCRYPTION_KEY` رمز می‌شود؛ کلید واقعی هنوز پیکربندی نشده است.
- **بازیابی مدیر:** کدهای بازیابی تصادفی، یک‌بارمصرف و فقط به‌صورت hash نگهداری شوند؛ مدیر آن‌ها را هنگام ثبت عامل دوم آفلاین نگه دارد. ایمیل به‌تنهایی مجوز حذف یا بازنشانی MFA نیست. اگر کدها از دست رفتند، بازیابی باید فرایند حضوری/خارج از برنامه، ثبت‌شده و همراه با ابطال نشست‌ها باشد؛ مسئولان مجاز این فرایند هنوز تعیین نشده‌اند.
- **Bale:** ورود و پیوند حساب خاموش می‌ماند. شناسه یا نام کاربری پیام‌رسان به‌تنهایی اثبات هویت و مجوز سفارش نیست. پیوند آینده فقط از نشست واردشدهٔ سایت، با رضایت صریح کاربر و تأیید کنترل حساب از راه API رسمی/قابل‌اعتبارسنجی پلتفرم انجام شود.

## وضعیت مخزن و شرط فعال‌سازی

- `src/auth.ts` اکنون Credentials provider مشروط دارد. `AUTH_LOGIN_ENABLED` پیش‌فرض `false` است؛ provider فعال نمی‌شود مگر AUTH_SECRET، SMTP، Redis/IP معتبر در تولید و کلید رمزگذاری MFA نیز معتبر باشند. صفحهٔ `/login` همان وضعیت واقعی آمادگی را نشان می‌دهد.
- Compose تولید، متغیرهای فعال‌سازی ورود، SMTP و کلیدهای MFA را از `.env.production` به سرویس وب می‌رساند؛ اگر `AUTH_LOGIN_ENABLED` تنظیم نشود مقدار پیش‌فرض `false` است. این فقط مسیر پیکربندی را آماده می‌کند و به‌تنهایی ورود را فعال نمی‌کند.
- در تولید، `AUTH_SECRET`، `RATE_LIMIT_SECRET` و `CRON_SECRET` باید secretهای یکتای URL-safe با حداقل ۳۲ نویسه باشند؛ کلید rate-limit باید صریح و جدا از `AUTH_SECRET` تنظیم شود و `AUTH_URL` باید origin معتبر HTTPS بدون مسیر، query یا fragment باشد. runtime و preflight پیشوندهای placeholder را بدون حساسیت به بزرگی حروف رد می‌کنند؛ endpoint زمان‌بندی نیز پیش از اجرای کار، secret نمونه یا تکراری را رد می‌کند. این بررسی محلی است و secretهای واقعی VPS خوانده نشده‌اند.
- جریان OTP شش‌رقمی ۱۰دقیقه‌ای فقط HMAC کد را ذخیره می‌کند، برای درخواست و بررسی از محدودیت‌های IP/ایمیل استفاده می‌کند و challenge را در تراکنش قفل‌شده مصرف می‌کند. حساب تازه با نقش `CUSTOMER` ساخته می‌شود؛ وضعیت/نقش حساب موجود از پایگاه‌داده بررسی می‌شوند.
- مدیر فقط با TOTP معتبر یا کد بازیابی استفاده‌نشده وارد می‌شود. راز TOTP رمز‌شده ذخیره می‌شود؛ کدهای بازیابی فقط HMAC می‌شوند و مصرفشان اتمیک است. مسیر راه‌اندازی اولیه با راز موقت `AUTH_ADMIN_MFA_ENROLLMENT_SECRET` یک نشست محدود و ۱۰دقیقه‌ای می‌سازد؛ این نشست به صفحات/APIهای مدیریتی دسترسی ندارد و راز bootstrap پس از فعال‌شدن TOTP باید از محیط حذف شود.
- guard صفحات مدیریتی و هر هفت API مدیریتی `mfaVerified` را بررسی می‌کنند؛ callback نشست، نقش و وضعیت کاربر را از پایگاه‌داده بازبینی می‌کند و در خطای DB دسترسی را می‌بندد.
- طرح و migration محلی ساخته و `prisma validate`/`prisma generate` اجرا شده‌اند؛ migration روی هیچ پایگاه‌داده‌ای اعمال نشده است. آزمون‌های واحد TOTP، رمزگذاری راز، اعتبارسنجی/هش کد، سیاست MFA و سقف تلاش اضافه شده‌اند؛ مسیرهای transaction با DB واقعی و ارسال SMTP واقعی end-to-end آزموده نشده‌اند.
- نام متغیرهای SMTP و کلیدهای MFA در نمونه‌های محیط ثبت شده‌اند، اما مقدار واقعی/سرویس فرستنده در دسترس این بررسی نیست و هیچ ایمیلی ارسال نشده است. مسئولان مجاز بازیابی اضطراری مدیر نیز مشخص نیستند.
- تا فراهم‌شدن SMTP و رازهای واقعی، مرور مستقل، آزمون یکپارچهٔ پایگاه‌داده و تعیین فرایند بازیابی، `AUTH_LOGIN_ENABLED` را خاموش نگه دارید؛ migration را به تولید اعمال نکنید.

این سند مجوز ارسال ایمیل، تغییر تولید یا بازکردن قابلیت‌های فروش نیست.

## پیوند احتمالی حساب بله — بررسی مستندات رسمی، ۳۰ اکتبر ۲۰۲۶

- مستند رسمی Bot API بله، API مبتنی بر HTTP و هم‌خانوادهٔ Telegram Bot API را شرح می‌دهد. ساخت ربات و دریافت token از BotFather انجام می‌شود؛ دریافت update از طریق `getUpdates` یا webhook ممکن است. لینک شروع `ble.ir/<bot_username>?start=<parameter>` باعث ارسال پیام `/start <parameter>` به ربات می‌شود. فیلدهای مستندشدهٔ کاربر شامل شناسهٔ بله هستند و شمارهٔ تلفن در شیء User مستند نشده است.
- مستند رسمی سفیر، سرویس سازمانی جداگانه‌ای برای ارسال پیام با شمارهٔ تلفن معرفی می‌کند که به دسترسی تجاری و Api Access Key سازمان نیاز دارد؛ مستندات همچنین هزینهٔ متفاوت قالب‌های خدماتی و تبلیغاتی و لزوم تأیید برخی قالب‌ها را ذکر می‌کنند، اما قیمت دقیق قابل اتکایی در صفحهٔ عمومی مشخص نشده است. این سرویس را نباید معادل اتصال عادی کاربر به Bot API فرض کرد.
- شرایط رسمی استفاده، API غیررسمی یا مهندسی معکوس و هرزنامهٔ سازمان‌یافته را منع می‌کنند. پیش از پیاده‌سازی باید مالک حساب، روش رضایت/لغو اتصال، هدف و مدت نگهداری شناسهٔ بله، مجوزها و هزینه‌های احتمالی مشخص شوند.
- طرح پیشنهادیِ هنوز پیاده‌سازی‌نشده: اتصال از نشست واردشدهٔ وب‌سایت آغاز شود؛ سرور nonce تصادفی، کوتاه‌عمر و یک‌بارمصرف بسازد؛ کاربر آن را با لینک رسمی start به ربات بفرستد؛ پس از تطبیق nonce و تأیید کاربر، شناسهٔ `from.id` ربات به حساب وب متصل شود. لینک start به‌تنهایی اثبات مالکیت حساب وب نیست و شمارهٔ تلفن از آن استنتاج نمی‌شود.
- هیچ BotFather token، کلید سفیر یا پیام واقعی در دسترس نیست؛ رباتی ساخته/فراخوانی نشده، پیام ارسال نشده و کدی تغییر نکرده است. پیاده‌سازی تا تصمیم مالک دربارهٔ رضایت، نگهداری داده و مسیر موردنیاز (Bot API یا سفیر) باز می‌ماند.

## بازبینی ایستای محلی — ۳۰ اکتبر ۲۰۲۶

- جست‌وجوی همهٔ ۷ فایل `route.ts` زیر `src/app/api/admin` وجود شرط `mfaVerified` را نشان داد. هر ۱۲ صفحهٔ عادی زیر `src/app/admin` از `requireActiveAdmin` استفاده می‌کنند؛ صفحهٔ `/admin/mfa/setup` جداگانه نقش/وضعیت مدیر و نشست محدودِ راه‌اندازیِ دارای انقضا را بررسی می‌کند.
- جست‌وجوی نقش مدیر بیرون از این مسیرها دو دسترسی دیگر را یافت: خواندن تصویر خصوصی کالا و مشاهده/پیام‌دادن در گفتگوی پشتیبانی. در `src/app/api/product-images/[imageId]/route.ts`، `src/app/support/cases/[caseId]/page.tsx` و `src/app/api/support/cases/[caseId]/messages/route.ts` دسترسی مدیر اکنون به `mfaVerified` وابسته است؛ مسیر مشتری و فروشنده تغییر نکرد.
- در مسیر درخواست کد، بررسی same-origin، خواندن محدودشدهٔ JSON، محدودسازی IP و ایمیل و پاسخ عمومی برای ایمیل معتبر دیده شد. در مسیر مصرف، قفل ردیف challenge، انقضا، سقف تلاش و حذف challenge پس از موفقیت در کد وجود دارد. کد TOTP با TOTP استاندارد و کدهای بازیابی با HMAC و مصرف اتمیک پیاده شده‌اند.
- فایل‌های تست موجود را فقط خواندم: آن‌ها helperهای اعتبارسنجی، hashing، policy، TOTP، رمزگذاری secret و بخشی از rate limit را پوشش می‌دهند. مسیرهای واقعی درخواست/مصرف کد با دیتابیس، replay و رقابت تراکنش‌ها، مصرف دوبارهٔ recovery code، مدیریت نشست پس از تغییر نقش و ارسال SMTP در این فایل‌ها آزمون یکپارچه ندارند.
- این بازبینی فقط ایستا بود و هیچ تستی در این نوبت اجرا نشد. SMTP و secretهای واقعی در دسترس نیستند، migration محلی به تولید اعمال نشده، و `AUTH_LOGIN_ENABLED` همچنان باید خاموش بماند تا آزمون یکپارچه و مرور مستقل انجام شود.

## بررسی امکان آزمون پایگاه‌دادهٔ ایزوله — ۳۰ اکتبر ۲۰۲۶

- در بررسی محیط محلی، یک پردازهٔ `postgres` روی پورت ۵۴۳۲ و آدرس‌های همهٔ رابط‌ها دیده شد؛ تعلق آن به این پروژه یا امن‌بودن استفاده از آن تأیید نشد، بنابراین اتصال یا پرس‌وجو انجام نشد.
- Docker CLI ویندوز در PATH نیست. Docker CLI در WSL به `unix:///var/run/docker.sock` اشاره می‌کند، اما `docker ps` با `permission denied` به سوکت محلی نرسید. در نتیجه این محیط در حال حاضر دیتابیس آزمایشیِ ایزوله و قابل‌شناسایی برای آزمون یکپارچه فراهم نمی‌کند.
- هیچ دیتابیسی، migration، سرویس یا محیط تولید تغییر نکرد. آزمون‌های DB/transaction همچنان بازند؛ تا فراهم‌شدن دیتابیس آزمایشیِ جداگانه، `AUTH_LOGIN_ENABLED` در تولید باید خاموش بماند.

## وضعیت هاست ایمیل برای جانان‌کده — ۳۰ اکتبر ۲۰۲۶

- مالک پروژه می‌گوید هاست ایمیل برای چند دامنهٔ میزبانی‌شده مشترک است؛ `sarayebarekat.ir` دامنهٔ اول و `janankadeh` دامنهٔ دومِ موردنظر است.
- هنوز مشخصات SMTP یا تأیید اضافه‌شدن دامنه و صندوق جانان‌کده به cPanel در دست نیست. تصویر فعلی File Manager را نشان می‌دهد، نه تنظیمات mail client؛ بنابراین از نشانی پنل، SMTP hostname یا پورت استنتاج نمی‌شود.
- رمز SMTP باید فقط در محل امنِ پیکربندی وارد شود و نباید در گفتگو فرستاده شود. تا آماده‌شدن صندوق، تنظیمات SMTP و DNS لازم و آزمون کنترل‌شده، ایمیل زنده‌ای ارسال نشده و `AUTH_LOGIN_ENABLED` تولید باید خاموش بماند.

## به‌روزرسانی صندوق مدیر — ۲۱ نوامبر ۲۰۲۶

- مالک پروژه ساخت صندوق `admin@janankadeh.ir` را در cPanel تأیید و دریافت/ارسال آزمایشی را گزارش کرد. تصویر تنظیم mail client مقادیر `ilh10.airdns.com`، پورت SMTP برابر `465` و SSL/TLS را نشان می‌دهد؛ تصویر Gmail نیز SPF، DKIM و DMARC را `PASS` نشان می‌دهد و مالک گزارش کرده پیام آزمایشی دیگر وارد Spam نمی‌شود.
- مقادیر غیرمحرمانهٔ SMTP در `.env.production.example` ثبت شدند. رمز صندوق در اختیار پروژه نیست و نباید در گفتگو فرستاده شود؛ هنوز آزمون ارسال OTP از خود برنامه یا تنظیم `.env.production` واقعی انجام نشده است. بنابراین ورود تولید همچنان باید خاموش بماند.
- ساخت صندوق ایمیل به‌تنهایی حساب سایت نمی‌سازد. حساب `admin@janankadeh.ir` باید ابتدا در برنامه با OTP تأیید شود و سپس ارتقای نقش و ثبت رویداد ممیزی از مسیر production مجاز و محدود انجام شود؛ پس از آن مدیر باید MFA و کدهای بازیابی را ثبت کند.

## هم‌قفل‌کردن ثبت MFA — ۳۱ اکتبر ۲۰۲۶

- بازبینی محلی یک رقابت میان شروع و تأیید ثبت TOTP یافت: دو مسیر روی ردیف‌های متفاوت قفل می‌گرفتند، پس شروعِ هم‌زمان می‌توانست عامل تازه‌فعال‌شده را دوباره pending کند. مسیر شروع اکنون ردیف `AdminTotpFactor` را هم قفل می‌کند و بعد وضعیت آن را می‌خواند.
- ESLint فایل مسیر و TypeScript موفق شدند. هیچ تست، دیتابیس، SMTP یا محیط تولیدی در این بررسی اجرا/تغییر داده نشد؛ تأیید رفتاری با PostgreSQL ایزوله هنوز لازم است.
